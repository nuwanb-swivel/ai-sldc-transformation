What is spec-driven development

Spec-driven development means the intent gets written down before any code exists. Not a ticket title, a spec: a brief, a PRD, a design system, an architecture decision. Each one is a durable artifact that an agent, or a person, can build against and be checked against later.

The alternative is what most AI-assisted coding looks like today: a prompt, a guess, and a diff. It works until nobody remembers why a decision was made, or two stories quietly implement the same rule two different ways. Writing the spec first removes the guessing, for the agent and for the reviewer.

Getting here is a transition, not a rewrite

You've seen where most companies start, and watched one idea go all the way through. Here's how a team actually moves from the first column to the third, without a mandate or a rewrite.

01

Pilot one real project

Pick a single, real, low-risk project. Run it through the full pipeline, spec to shipped, with one written definition of done. Nothing else in the org changes yet.

02

Name the skills, not a new team

Turn the pilot's steps into fixed, repeatable skills: brief, PRD, UX, architecture, stories, build. Same people, same tools, an artifact trail that wasn't there before.

03

Expand by project, not by mandate

New work opts in as it starts. Legacy systems keep their existing process until they're touched anyway. Nobody is asked to rewrite what already works.

04

Make it the default

Once two or three teams have shipped this way, spec-driven becomes the default path for new work, and an unspecified change becomes the exception that needs explaining.

Common objections, answered directly

QDoesn't writing a spec first slow the first project down?

Yes, a little, on purpose. Every stage after that is faster, because nothing gets re-explained, re-decided, or reverse-engineered from a diff.

QWhat about our existing legacy systems?

They keep their current process until they're touched anyway. Nobody is asked to retrofit a spec onto code that already works.

QWhat if the spec turns out to be wrong?

That's cheaper to fix than wrong code. It's one document to correct, not a rewrite scattered across files with no record of why.

QDoesn't this just move the bottleneck to human review?

Deliberately, yes. The review points are fixed and small: approve scope, confirm architecture, review code. Not a rewrite of anyone's judgment.
