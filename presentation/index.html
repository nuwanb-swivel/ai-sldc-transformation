Chapters

    Governance

    How we govern the project

    The process is fixed on purpose — the same skills, in the same order, producing the same kind of traceable artifact, on every project. That's what makes the output predictable enough to hand to a client.

    One rulebook per repo

    AGENTS.md is checked into the repo and defines the Definition of Done once — lint, build, unit tests, end-to-end tests, UI verification. Every change is held to it, whether written by a person or an agent.

    A fixed skill for each stage

    Brief, PRD, UX, architecture, story breakdown, sprint planning, build, code review, and retrospective are each a named, repeatable skill — not an ad-hoc conversation reconstructed from scratch each time.

    Traceability, end to end

    Every functional requirement traces from the brief, through the PRD, into an architecture decision, into a story's acceptance criteria, into a test. Nothing gets built that a spec can't be pointed to.

    Assumptions are decisions, not guesses

    Anything the brief or PRD left open is tagged inline ([ASSUMPTION], [NON-GOAL]) and resolved explicitly with the product owner — never silently picked and buried in code.

    Conflicts get recorded, not smoothed over

    When the UX spec and the PRD disagreed on how the admin status control should behave, the resolution — and which document won — was written into epics.md, so the decision survives the conversation that made it.

    Progress is one file, not tribal knowledge

    sprint-status.yaml tracks every story through backlog → ready-for-dev → in-progress → review → done, mirrored on the team's Paneo board — so status is a fact, not a status-meeting answer.

    Architecture decisions are binding

    Each of the nine architecture decisions states what it exists to prevent — e.g. authorization logic drifting into the UI layer — so two stories can't quietly implement the same concern two different ways.

    Review before done

    Every story gets a fresh-context code review before it's marked done — checking correctness and architecture compliance, not just whether it runs.

    Verification

    Verified before it ships

    The same six gates run on every pull request — nothing merges to main unless all of them are green.
